### Invarianti residui prima delle Responses reali

#### 1. Restart/crash recovery dei run

Oggi il restart testato avviene a run completati.

Manca una policy esplicita per run persistenti lasciati:
- `queued`;
- `streaming`;

da un processo che cade.

Prima del provider reale non voglio run orfani né retry che possano duplicare una chiamata provider.

Propongo:
- `queued` persistente non ancora iniziato → recuperabile/rieseguibile;
- `streaming` trovato al boot dopo crash → non rieseguire alla cieca; marcare `failed`/interrupted con cursor invariato, salvo futura strategia provider-specific verificata.

Serve test restart dedicato.

#### 2. Lifecycle dei conversation_id separati

Lo schema li separa per room/agente, ma il percorso reale non li crea/aggiorna ancora.

Serve un **fake provider stateful** che dimostri:
- conversation Tessa distinta da GPTina;
- aggiornamento solo dello stato dell'agente proprietario;
- `conversation_id_at_start` coerente nel run;
- nessuna modifica alla conversation dell'agente non selezionato.

#### 3. Bootstrap/identity server-side separati

Prima della rete reale voglio il caricamento server-side di due bootstrap distinti:
- Tessa;
- GPTina;

con nessuna possibilità che room content o output dell'altra istanza sostituiscano istruzioni privilegiate.

Il test deve dimostrare identity/bootstrap separation, non soltanto state separation.

#### 4. Provenienza run reale

Oggi campi come `model: unconfigured`, bootstrap/checkpoint e versioni sono ancora placeholder.

- `api_mode`;
- `model`;
- `bootstrap_version`;
- `checkpoint_ref` quando disponibile;
- `context_builder_version`;
- `conversation_id_at_start`.

#### 5. Delta coalescing provider

La persistenza-before-publish degli eventi applicativi è corretta.

Manca però ancora il layer che trasforma i micro-delta provider in chunk applicativi coalescati, come previsto dallo schema.
